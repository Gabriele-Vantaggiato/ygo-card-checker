# Accounts, Deck Sync & Serverless Pivot — Design

## Context

The 6-pillar semantic architecture (`feature/semantic-architecture` branch) shipped as
build-time enrichment + static JSON + client-side pure functions. This spec covers a
follow-up pivot requested by the user, correcting two false premises in the request
(MentionsCards and CardSynergies already exist — see below) and scoping the one
genuinely new subsystem: user accounts + deck sync + a synergy-improving cron.

## Part A — Serverless BFF (no new infra, executes immediately)

`deck-health-analyzer.utils.ts` and `deck-recommendation.utils.ts` (already written,
tested, pure) move behind two Vercel Edge Functions, same convention as the existing
`api/gemini/[...path].ts` (Web-standard `Request`/`Response`, `export const config =
{ runtime: 'edge' }`). Client posts `{ deckCardIds, quantities }`, gets back a small
JSON result instead of downloading `semantic.json` (3MB) to compute locally.

- `api/analyze-deck-health.ts` — wraps `analyzeDeckHealth`.
- `api/get-recommendations.ts` — wraps `getSuggestions`.

Both fetch `semantic.json` via relative `fetch()` against the deployed static asset
(not bundled — 3MB is too close to Edge Function bundle limits) with Edge cache
headers, so repeat invocations on a warm instance are free. `get-recommendations`
additionally queries `card_synergies` live from Supabase (see Part C) instead of a
static `synergies.json` — this is the one dataset that genuinely needs to be mutable
at request time (the cron writes to it), so it's the one migrated off static JSON.

## Part B — LLM-assisted parser (skeleton only, not executed)

`llm-semantic-parser.ts`: a `CardSemanticParserService` implementation using
Gemini structured output, prompted with PSCT rules (condition : cost ; effect).
Same `SemanticProfile` shape as the existing regex parser — drop-in alternative, not
a replacement. The regex `RuleBasedCardSemanticParser` stays as the free, instant
default; the LLM version is opt-in via a `--source=llm` flag on `tag-semantic.ts`,
only running for cards without a cached `source='llm'` row (the schema already has
this column). Mentioned card names come back as strings from the LLM (not IDs) —
name→ID resolution already happens in `build-relations.ts`'s existing mention-linking
pass; no new table.

Not executed against the real 14,641-card catalog in this pass — costs real API
money and needs a key the user hasn't provided. Delivered as reviewed, working code.

## Part C — Accounts, deck sync, sharing, synergy cron

### Backend: Supabase (new infra — provisioned this session)

Chosen over a custom REST layer: Postgres + Auth (email/password + Google OAuth) +
autogenerated REST, RLS enforces per-row security so the client SDK talks to Supabase
directly — no custom CRUD backend to write or maintain.

**Schema:**

```sql
create table decks (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  name text not null,
  cards jsonb not null,
  is_public boolean not null default false,
  share_slug text unique,
  updated_at timestamptz not null default now()
);
create index decks_user_id_idx on decks(user_id);
create unique index decks_share_slug_idx on decks(share_slug) where share_slug is not null;

alter table decks enable row level security;
create policy "owner full access" on decks for all
  using (auth.uid() = user_id) with check (auth.uid() = user_id);
create policy "public decks are readable by anyone" on decks for select
  using (is_public = true);

create table card_synergies (
  card_a integer not null,
  card_b integer not null,
  deck_count integer not null default 0,
  source text not null check (source in ('tournament', 'user_decks')),
  updated_at timestamptz not null default now(),
  primary key (card_a, card_b, source)
);
create index card_synergies_a_idx on card_synergies(card_a);
```

`card_a < card_b` invariant kept from the original sqlite table. `source` column
keeps tournament-derived rows (seeded once from the existing local `deck_cooccurrence`
sqlite data — real data, already scraped, just migrated) separate from
`user_decks`-derived rows (written by the cron) — the recommendations endpoint sums
both, but this keeps the provenance visible and re-seedable independently.

### Frontend: DeckSyncService

New service, same public shape as `DecklistService` so components don't need to
branch on auth state. On login: if local `DecklistStorage` has decks, upsert them all
to Supabase once, then switch the service's source of truth to Supabase for the rest
of the session (fetch-on-load, write-on-change — no realtime multi-tab sync, not a
requirement here). Guests keep using `DecklistService`/localStorage unchanged.

### Sharing: `/d/:slug` route

New standalone page, no auth. Reads one row via `share_slug` (RLS's public-select
policy makes this a plain anon-key query), renders the decklist read-only — reuses
existing decklist display components, new thin container component only.

### Cron: synergy aggregation

`vercel.json` gets a `crons` entry (weekly) hitting `api/cron/update-synergies.ts`
(Edge Function, Vercel signs cron requests — verify the signature, reject anything
else). It reads all `decks` rows (`cards` jsonb only, never exposed further), counts
pairwise co-occurrence across decks with the same aggregation logic as the existing
local `sync-tournament-decks.ts`, and upserts into `card_synergies` with
`source='user_decks'`.

## Out of scope (explicitly deferred)

- Realtime multi-tab deck sync.
- Public user profiles / browsing other users' decks (only the single-deck share link).
- Deleting/exporting account data flows (GDPR-style tooling) — flag for a follow-up
  once there's an actual user base, not needed to ship this.

## Testing

- Part A: unit tests already exist for the wrapped pure functions; add a thin
  request/response contract test per Edge Function (mock `fetch`/Supabase client).
- Part C: RLS policies verified via Supabase's own policy simulator / direct SQL
  test queries (a user cannot read another user's private deck; anon can read a
  public one) before any frontend code depends on them.
